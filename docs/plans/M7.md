# M7 plan: Unverified Claim check

Build plan: [M7](../build-plan.md). Terms: Unverified Claim, Briefing, Display Name, Playbook Rule,
Snapshot, Campaign Workspace, Player (see [GLOSSARY.md](../../GLOSSARY.md)). Input: the turn log of
[M3.md](M3.md) / [M5.md](M5.md) (`.hlidskjalf/turn-log.jsonl`, one JSON line per tool call).

**Done when** (from the build plan): a planted wrong district count is blocked, a normal Briefing
passes, and false positives on the reference Briefings stay at or below one per Briefing.

## Division of labour

| Code (`src/hlidskjalf/claims/`, `hooks/`) | Model |
|---|---|
| Finds the numbers and names in the final answer, normalises them, matches them against the turn's tool results, blocks, logs | Rewrites the answer after a block, using only what the tools returned |
| Decides everything by rule; no model call, no network | `hlidskjalf:review-blocks` (developer skill) sorts logged blocks into real errors and false positives and *proposes* changes; it edits nothing |

The check is a plain program with a fixed rule set. The same answer and the same turn log give the
same verdict, which is also what makes it testable on recorded Briefings.

## What the hook sees

A Stop hook gets JSON on stdin with `transcript_path`, `cwd`, `stop_hook_active` and, in current
Claude Code versions, the final assistant message. Increment 4 starts with a probe that records the
real input (and which of these fields exist) before the script relies on any of them; if the final
answer is not in the input, it is the last assistant text block of the transcript. Exit protocol:
`{"decision": "block", "reason": "..."}` on stdout, exit 0; allow = no output.

- **Where it runs.** Only inside a Campaign Workspace (the hook walks up from `cwd` to the first
  directory holding `campaign.yaml` and `.hlidskjalf/`). Anywhere else it allows silently, so the
  plugin does nothing in unrelated projects.
- **Evidence = the turn log entries of the session.** The window starts at the first transcript
  timestamp of the session and ends now. The build plan says "of the turn"; a follow-up question is
  answered from numbers of an earlier turn of the same conversation, and blocking that would be a
  false positive on every second question. Staleness is not this check's job (the consult skill's
  save-age guard handles it). The window is a single constant in one place, so the review skill can
  propose narrowing it if stale numbers slip through.
- **Player input is exempt.** Numbers and names that occur in the Player's own messages of the
  session (from the transcript) count as matched.
- **No tool result at all** and numbers in the answer: those numbers are unverified (except the
  exemptions below). An answer without numbers and names always passes.

## Extraction

### Numbers

A number is a token of digits with optional thousands separators, a decimal mark, a sign, a
percent sign or a magnitude suffix: `2794.45`, `2,794.45`, `2.794,45`, `7.4k`, `7,4 k`, `1.2M`,
`-18`, `+5`, `15 %`, `15%`. Each occurrence becomes a claim with the value, the stated precision
(number of decimals as written; for `7.4k` one decimal of thousands = 100) and the sentence it
stands in.

Separator rules, applied to the token only, no locale guess from the surrounding language
(the answer may mix both):

- one separator with exactly three digits after it and a group before: thousands (`2,794` and
  `2.794` are 2794) unless the leading group is `0` (`0.250` is a decimal);
- one separator otherwise: decimal mark;
- two kinds of separator: the one that appears last is the decimal mark, the other groups
  thousands (`2.794,45`, `2,794.45`);
- the same separator several times (`1.234.567`): thousands.

The ambiguous case `2.794` is read both ways: the claim matches when **either** reading (2794 or
2.794) is in the data. This avoids the most likely false positive, costs almost nothing in
strictness, and the review skill sees which reading matched.

### Not claims (never extracted)

- list numbering at the start of a line (`1.`, `2)`), headings numbers (`## 3. Strategy`), and
  numbers inside code spans that are file names, ids or commands;
- years and in-game dates shaped `2259.12.25` or `2259` (a date is matched as a whole string
  against dates in the data; a bare year in `2200` to `2500` is exempt as a date reference);
- numbers that are part of a Display Name or id that matched as a name (`Tier 2`, `Hangar 3`);
- digits inside the Playbook Rule ids and markdown link targets.

### Exempt (extracted, but allowed)

- Numbers in a **quoted Playbook Rule**: a markdown blockquote line (`> ...`) whose text matches a
  rule text in the tool results (the consult skill quotes rules this way). Rule text reaches the
  model through `expand_graph`, so it matches anyway; the exemption covers the model translating
  the quote into the Player's language.
- Numbers the Player wrote (see above).
- **Derived figures**, decided here from the M5 verification ("230.36 = 88 + 74.77 + 67.59"): a number
  is allowed when it is the sum or difference of 2 to 4 other numbers **that stand in the same
  list item, table row or paragraph** and that each match the data, or a percentage `a / b * 100`
  of two such numbers. Compared within the rounding of the least precise operand. So the model
  may compute, but must show its addends; an unexplained total is blocked, and the block reason
  says "show the addends or quote the tool's figure". Products and other formulas are not allowed
  in v1 (the review skill will tell us if they are common).

### Names

Name candidates are only spans the answer marks as a thing: `**bold**`, `` `code` `` and quoted
text (`"..."`, `„..."`, `«...»`) inside a sentence, plus table cells in a column headed Name.
Not whole-line bold (headings and labels such as `**Strategie**`), not a span of one lowercase
common word. Capitalised word runs in running text are **not** extracted: in German every noun is
capitalised, so that rule would drown the check in false positives. The price is that a name the
model writes without any marking is not checked; the consult skill therefore asks for bold on
every Display Name, which is a small edit made in increment 6 (with the static skill test
updated, not weakened).

A candidate name matches when, compared case-insensitively with markup stripped, it equals a
Display Name or text string in the evidence: any string value in a tool result (empire names,
planet names, building and technology names, node titles, Goal titles, rule ids). Fuzzy matching
is limited to singular/plural `s` and a trailing `:`. A name that is the id of a node or rule
(`unity.more`, `unity-vs-next-tradition`) matches against ids as well.

## Matching a number

The evidence index is built once from the window's tool results: every number in every result
(JSON numbers, and numbers inside strings such as evidence texts and rule bodies), with the
precision at which the tool gave it. A claim matches when some data value rounds to the claim at
the claim's stated precision:

- `7.4k` matches data in [7350, 7449.99] (stated precision 100); `2794` matches `2794.45`;
  `2794.45` does not match `2794.4` or `2794.5`.
- a percent claim `15%` matches data `15`, `0.15` with percent meaning, or `15.0`; a ratio data
  value `0.15` matches claim `15%` only when the tool field is a known ratio (the metrics
  registry marks them); without that mark both readings are tried and recorded.
- sign is ignored for matching and kept for the report (`-18` against data `18` in an upkeep
  field is common phrasing).
- counts: an integer claim matches an integer data value exactly, or the length of a list in the
  result when the tool field names it (`planets`, `districts`); the planted-district-count test
  in this milestone relies on exact match.

Anything that does not match is an **Unverified Claim**.

## Block, log, loop guard

- On any Unverified Claim the hook blocks. The `reason` is shown to the model: a short
  list in English (`"2794.45"` not found in any tool result of this session; context sentence;
  nearest data value if one exists within 10 % relative), and the instruction "Rewrite the answer
  using only figures and names from the tool results, or call a tool to get them. Do not mention
  this check to the Player." (Per CLAUDE.md the Display Name rule is untouched: the check never
  outputs a key.)
- Every block is appended to `<workspace>/.hlidskjalf/blocks.jsonl`: timestamp, session id,
  answer hash, each claim (kind number/name, text, normalised value, precision, sentence, nearest
  data value), whether `stop_hook_active` was set, and `released`. One line per block.
- **Loop guard.** The hook blocks at most twice per answer. If `stop_hook_active` is true and the
  claims are still unverified, it releases the answer, logs `released: true`, and prints
  `systemMessage` telling the Player in one sentence that the answer holds unchecked figures.
  A check that cannot be satisfied must not trap the session.
- Hook crash or unreadable input: allow, and log to `.hlidskjalf/hook-errors.log`. A broken check
  never silences the Coach, and `tests` assert that a thrown exception still exits 0 with no block.

The Python code sits in `src/hlidskjalf/claims/` (`extract.py`, `normalise.py`, `evidence.py`,
`check.py`, `blocks.py`). `hooks/hooks.json` runs
`uv run --quiet --project ${CLAUDE_PLUGIN_ROOT} hlidskjalf hook stop`, and `plugin.json` names
`./hooks/hooks.json`. The CLI command `hlidskjalf claims check --workspace DIR --answer FILE` runs
the same function from the shell (developer use, and how the recorded Briefings are replayed).

## `hlidskjalf:review-blocks` (developer skill)

`skills/review-blocks/SKILL.md`, not for the Player. Command `hlidskjalf blocks summary
--workspace DIR` prints `blocks.jsonl` grouped (by kind, by reason code: `no_match`,
`near_match`, `derived_unexplained`, `name_no_match`, `released`), with counts and the answer
sentence for each. The skill then has the model classify each group as a real error (the model
invented or mis-rounded) or a false positive, and write a proposal per group into
`docs/proposals/claims.md`: a change to the extractor, to the check, or to a Playbook Rule. It
never edits code, knowledge or tests itself (same hold point as `docs/proposals/playbook.md`).

## Tests

- **Normalisation** (pure): every spelling above, both separator orders, `7.4k`, percent, sign,
  ambiguous `2.794` read both ways, precision rounding boundaries.
- **Extraction**: what is a claim and what is not (list numbers, headings, dates, ids, links, code
  spans), name spans (bold, code, quotes) versus headings, a German sentence full of capitalised
  nouns yields no name claims.
- **Matching** on synthetic turn logs: exact, rounded, thousands, k suffix, percent, sign, a wrong
  number blocked with the nearest data value, derived sum with shown addends allowed, the same
  total without addends blocked, a different total with addends blocked, Player input exempt, a
  quoted rule exempt, no tool results.
- **Hook**: stdin JSON in, stdout JSON out, exit code, `blocks.jsonl` line, loop guard, outside a
  workspace allows silently, malformed input allows, `stop_hook_active` path.
- **Reference Briefings** (built by the test from the git-ignored vulkan saves and skipped without
  them; never committed, because they hold player names): the planted
  wrong district count is blocked; the recorded M5 Briefing passes except at most one claim; a
  count of false positives over every reference Briefing is asserted to be at most one each.
- **Wiring**: `hooks/hooks.json` is valid, the command exists as a CLI sub-command, `plugin.json`
  references it, and the `review-blocks` skill has frontmatter and names only commands that exist.

## Increments (order and checks)

1. **This plan**: docs only.
2. **Normalisation and extraction.** `claims/normalise.py`, `claims/extract.py`: numbers with
   precision, names, the not-a-claim and exempt rules (derived figures are matched in
   increment 3). Check: the pure tests above.
3. **Evidence and matching.** `claims/evidence.py` (index from turn log entries, Player input),
   `claims/check.py` (match, derived sums and percentages, rule quotes, nearest value, reason
   codes) and the `hlidskjalf claims check` CLI. Check: matching tests on synthetic turn logs.
4. **The Stop hook.** Probe the real hook input first and record it in the plan's open risks if it
   differs; `hooks/hooks.json`, `hlidskjalf hook stop`, workspace detection, block output,
   `blocks.jsonl`, loop guard, crash-safe exit, `plugin.json`. Check: the hook tests, driving the
   script with stdin exactly like Claude Code does.
5. **`review-blocks`.** `claims/blocks.py` (grouping), the `blocks summary` CLI,
   `skills/review-blocks/SKILL.md`, `docs/proposals/claims.md` (empty), static skill test. Check:
   grouping tests on a fixture `blocks.jsonl`, skill test.
6. **Verification.** Consult skill asks for bold Display Names (static test updated); replay the
   recorded M5 headless Briefing and a planted wrong district count; a fresh headless `claude -p`
   Briefing with the hook live, in a temp workspace as in M5, counting blocks and false
   positives; numbers in the Log. Anything the check blocks wrongly is fixed in the check if the
   fix is a general rule, otherwise recorded in `docs/proposals/claims.md`.

Each increment ends with the full suite (`HLIDSKJALF_PERF_SLACK=1.5`) and ruff.

## Open risks

- **Name checking is only as good as the marking.** Unmarked names are not checked; the skill
  asks for bold, and increment 6 counts how often the model complies.
- **Evidence window too wide.** A stale number from an earlier read passes. Mitigation: the save
  age guard; the window constant is one line to narrow.
- **Rounded figures in prose** (`etwa 2,8k`) lose precision on purpose; the claim is matched at
  its own precision, so a coarse claim is easy to satisfy. That is intended: the check is for
  invented figures, not for bad rounding style.
- **Hook input shape.** Probed in increment 4 on Claude Code (headless `claude -p`, throwaway Stop
  hook dumping stdin): `session_id`, `transcript_path`, `cwd`, `prompt_id`, `permission_mode`,
  `effort`, `hook_event_name`, `stop_hook_active`, `last_assistant_message` (the final answer, so the
  transcript fallback is rarely needed), `background_tasks`, `session_crons`. After a block the
  next Stop event has `stop_hook_active: true` and the rewritten answer; the flag stays true for
  every further pass, so the "block at most twice" count comes from `blocks.jsonl` (same
  `session_id` and `prompt_id`, not released), not from the flag. Transcript lines carry
  `timestamp` (also the `queue-operation` lines the window starts from). The plugin manifest
  naming `./hooks/hooks.json` is accepted; Claude Code says the standard file loads on its own and
  loads it once. The command uses exec form (`command` + `args`), because `claude plugin validate`
  warns about an unquoted `${CLAUDE_PLUGIN_ROOT}` in a shell command.
- **Block loops.** Covered by the loop guard (two blocks, then release with a notice).
- **Number words** (`drei`, `three`) are not checked in v1; the review skill will tell us if
  invented counts appear that way.
