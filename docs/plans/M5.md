# M5 plan: Huginn in Consulting mode

Build plan: [M5](../build-plan.md). Terms: Briefing, Situation, Goal, Symptom, Horizon, Cause,
Root Cause, Remedy, Obstacle, Actionable, Pending, Key Action, Strategy, Action Plan, Solution
Graph, Vicious Circle, Crisis, Playbook Rule (see [GLOSSARY.md](../../GLOSSARY.md)). Decisions:
[ADR 0003](../adr/0003-mechanics-graph-built-per-version-by-developer.md), M4 formats in
[M4.md](M4.md).

**Done when** (from the build plan): a Briefing on the reference mid-game save is correct by
the golden values, cites Playbook Rule ids, and does not recommend spending Unity that is saved
for the next Tradition. "Correct by the golden values" is a hold point (the values are Julian's,
see `docs/awaiting-julian.md`); everything else is checked by tests and one headless Briefing.

## Division of labour

The code does what must be identical every time; the model does what needs judgement.

| Code (`graph/`, MCP) | Model (`hlidskjalf:consult`) |
|---|---|
| Walks the Mechanics Graph from chosen Goals | Reads the Situation, picks the Goals and their Horizons |
| Evaluates each checkable Obstacle against the Snapshot | Weighs Obstacles that are `judgement_only` or unchecked |
| Marks Remedies Actionable, Pending or obstructed | Prunes what does not fit this empire, with a reason |
| Finds Vicious Circles and their break point | Adds missing nodes with `source: "model"` |
| Ranks Key Actions by a fixed rule | Writes Strategy and Action Plan in the Player's language |
| Validates the Solution Graph | Quotes Playbook Rules, states only numbers from tool results |

Fair Play: expansion reads only the Tracked Empire's own numbers (the metrics registry has no
path into rival intel), so it cannot leak hidden facts.

## Expansion (`src/hlidskjalf/graph/expand.py`)

```python
expand_graph(graph, goals, extract, *, crisis_goals=(), depth_limit=5) -> Expansion
```

`goals` are Goal ids from the Mechanics Graph; an unknown id is returned in `unknown_goals`
(the model may still add it as a model Goal) and never raises. `extract` is one Snapshot
extract. The function is pure and deterministic: no clock, no randomness, sets are sorted
before they are walked, file order of the YAML is the tie-breaker.

### Evaluating checks

`evaluate(comparison, graph.metrics, extract)` returns a `Check`:

| `state` | When |
|---|---|
| `present` | the comparison is true: the Obstacle holds |
| `clear` | the comparison is false |
| `unknown` | a metric resolves to `None` (field missing in the extract) |
| `judgement` | `check: {judgement_only: true}` |

A `Check` carries the metric names, the resolved values and the operator, so the Briefing can
state "Unity 412, next Tradition 650" from the tool result (these are the numbers the
Unverified Claim check will match). Division by zero in a ratio resolves to `None`, hence
`unknown`, never a crash.

### Walk

1. **Breadth-first** from the Goals, so a node's depth is its shortest distance from any Goal;
   merging by id is automatic (one node however many parents). Depth counts the Cause, Remedy
   and Obstacle nodes on the path; the Goal is depth 0, its Causes depth 1.
2. **Depth limit 5.** A node first reached at depth 5 is kept but not expanded: it gets
   `too_far: true` if it has outgoing links, and the Briefing says "too far for this Horizon".
   Measured on the current graph without any pruning, 7 to 16 of 27 to 41 nodes per Goal lie
   deeper than 5 (maximum depth 9, `slots.more` is 3), so most of what is cut are the
   Obstacles-of-Obstacles chains; the increment records the actual counts on the reference save.
3. **Obstacles are expanded only when they hold or are undecided.** `present`, `unknown` and
   `judgement` Obstacles descend into their Remedies; a `clear` Obstacle stays as a leaf with
   its evidence (so the model can say "not a problem here: Unity 900 against 650") and its
   Remedies are not walked. This is also what makes Vicious Circles data-dependent: a circle
   broken by a clear Obstacle is not reported.
4. **Remedy status**, from its Obstacles:
   - `obstructed`: at least one Obstacle is `present`.
   - `pending`: some Obstacle is `present`, **and** `pending_when` is true. (The M4 plan says
     "Pending when true and the Obstacles are not"; read together with the glossary, Pending
     means "will become Actionable on its own", i.e. obstructed today but the `pending_when`
     condition says it resolves within the Horizon. A Remedy with no present Obstacle is
     Actionable whatever `pending_when` says.)
   - `actionable`: no Obstacle is `present`.
   Obstacles that are `unknown` or `judgement` do not change the status; they are listed in the
   Remedy's `unchecked` so the model weighs them and the Briefing says they were not checked
   against numbers.
   Pending is treated like Actionable for Key Actions (glossary), but stays visible as Pending.
5. **Vicious Circles** = strongly connected components (Tarjan, iterative) of size > 1 or with a
   self-link in the expanded subgraph. Name = the shared `circle:` value of the members (the
   most frequent one if members disagree; the validator already warns on unnamed cycles), else
   `circle:<first member id>`. `break_point` = the member with `break_point: true`; none marked →
   the Remedy with the lowest `cost`, then highest `strength`, then id. A circle with no
   Remedy member is reported without a break point and flagged for the model.
6. **Key Action candidates**: every Remedy with status `actionable` or `pending`.
   - `serves`: the Goals from which the Remedy was reached (all of them, thanks to merging).
   - `unlocks`: obstructed Remedies for which this Remedy is a Remedy of a `present` Obstacle,
     i.e. the next step on the Strategy path.
   - Ranking key, descending in importance: serves a Crisis Goal (`crisis_goals` passed by the
     model, since the Crisis is a judgement about the Situation) → number of Goals served →
     `strength` → `speed` → lower `cost` → `actionable` before `pending` → node id.
     (high > medium > low; for cost low > medium > high.) A Remedy that is only
     `unlocks` something still ranks by its own ratings.
7. **Output** (`Expansion.to_dict()`, plain JSON, sorted by depth then id for stability):

```json
{
  "version": "v4.5.2", "date": "2259.12.25",
  "goals": [{"id": ..., "title": ..., "symptoms": [{"metric": ..., "value": ...}], "crisis": false}],
  "unknown_goals": [],
  "nodes": [{"id": ..., "type": ..., "title": ..., "text": ..., "depth": 2, "status": "actionable",
             "check": {"state": "present", "metric": ..., "op": "<", "values": {...}},
             "unchecked": [...], "too_far": false, "ratings": {"strength": ..., "speed": ..., "cost": ...},
             "rules": [...], "effects": [...], "circle": null}],
  "edges": [{"from": ..., "to": ..., "kind": "cause|remedy|obstacle"}],
  "circles": [{"id": ..., "members": [...], "break_point": ...}],
  "key_action_candidates": [{"rank": 1, "node": ..., "serves": [...], "unlocks": [...]}],
  "playbook_rules": {"<id>": {"reason": ..., "body": ...}},
  "warnings": []
}
```

- `text` = `description` (Cause, Obstacle) or `judgement` (Remedy), as the author wrote it.
- `effects` = up to five of the node's linked generated facts as
  `{source, modifier, amount, amount_kind, requirement}` (Display Name of the source, never a
  key), `more: n` for the rest. This is how a Briefing gets "Supremacy: +20 naval capacity" from
  a tool result instead of from memory. If the output exceeds the 40k-character budget of an
  extract, effects drop to three per node first.
- `playbook_rules` = the full text of every rule cited on any returned node: the skill quotes
  these (quoted Playbook Rules are exempt from the Unverified Claim check).
- Benchmarks are not read. Nothing else about other empires is read.

### Tests (`tests/test_expand.py`, small synthetic packs plus the real graph)

- Synthetic pack, hand-made extract: Obstacle present/clear/unknown/judgement each give the
  right Remedy status; Pending only with a present Obstacle and a true `pending_when`; a `clear`
  Obstacle's Remedies are not walked; depth 5 marks `too_far` and does not expand beyond it.
- A merged node (two parents) appears once with both parents as edges and `serves` of both Goals.
- A two-node loop is returned as one Vicious Circle with the `break_point` node; a loop broken
  by a clear Obstacle is not returned.
- Ranking: Crisis Goal first, then Goals served, then ratings; ties by id; the function is
  stable under shuffled goal order.
- Determinism: `json.dumps(expansion.to_dict(), sort_keys=True)` is identical across two runs
  and across a permuted `goals` list.
- Real graph, reference extract (skips without the saves): `naval_capacity.more` expands, the
  Supremacy Remedy is `obstructed` or `actionable` exactly as `unity.stockpile` vs
  `traditions.next_cost` says (computed independently in the test from the extract), and every
  returned number sits in `check.values` or `effects`.
- `resolve_metric` moves without changing `benchmarks` behaviour (existing tests stay green).

## Solution Graph (`src/hlidskjalf/graph/solution.py`, `solution.schema.json`)

The Solution Graph is the Briefing's merged network (glossary) and the only input M6 renders.
It is a JSON document, `solution-graph.json`, written next to the Briefing in the workspace
(`briefings/<in-game date>/solution-graph.json`).

```json
{
  "schema": 1, "game_version": "v4.5.2", "date": "2259.12.25", "empire": "...",
  "nodes": [
    {"id": "naval_capacity.more", "type": "goal", "source": "graph", "title": "...", "horizon": "short", "crisis": false},
    {"id": "naval_capacity.adopt_supremacy", "type": "remedy", "source": "graph", "title": "...",
     "status": "obstructed", "evidence": [...], "rules": ["unity-vs-next-tradition"]},
    {"id": "model.fleet_upkeep_too_high", "type": "cause", "source": "model", "title": "...",
     "reason": "why this is not in the Mechanics Graph", "evidence": [...]}
  ],
  "edges": [{"from": "...", "to": "...", "kind": "cause|remedy|obstacle"}],
  "circles": [{"id": "food_needs_pops", "members": [...], "break_point": "..."}],
  "key_actions": [{"rank": 1, "node": "...", "serves": [...], "unlocks": [...], "why": "..."}],
  "pruned": [{"id": "...", "reason": "..."}]
}
```

Rules enforced by the JSON Schema and by the validator
(`validate_solution_graph(doc, graph, rules) -> list[Problem]`, same `Problem` type as the
Mechanics Graph validator):

- **Source marking.** Every node has `source: "graph"` or `"model"`. A `model` node must carry
  `reason` (non-empty) and its id starts with `model.` so it can never collide with a graph id;
  a `model` node carries no `facts`, no `status` computed by code and no `rules`. A node
  claiming `source: "graph"` must exist in the Mechanics Graph with the same `type`. This is the
  validator that rejects malformed graphs, and the one that catches an invented Playbook Rule id
  (`rules` entries must exist in the loaded rules).
- **Grammar.** Edge kinds follow the Mechanics Graph (goal → cause; cause → cause|remedy;
  remedy → obstacle; obstacle → remedy). An edge between two `graph` nodes must exist in the
  Mechanics Graph; an edge touching a `model` node is allowed if the grammar holds.
- **Roots and reachability.** Only Goals are roots; every non-Goal node is reachable from a
  Goal; every id used by an edge, circle, key action or pruned entry exists.
- **Key Actions** reference Remedy nodes only, with a unique `rank` 1..n, and each has at least
  one Goal it serves. A graph-sourced Key Action must be `actionable` or `pending`; a model-added
  Remedy may be one when its `evidence` is non-empty.
- **Horizons.** Goals have `horizon` in `short | medium | long`.
- Unknown properties are rejected, so a renamed field breaks loudly (M6 depends on the shape).

### Composing instead of hand-copying

Writing 30 to 40 nodes by hand in the skill would cost tokens and invite typos. The skill hands
`compose` a small overlay and gets the validated document back:

`compose(expansion, overlay) -> solution_graph` with
`overlay = {goals: {id: {horizon, crisis}}, prune: [{id, reason}], add_nodes: [...], add_edges:
[...], exclude_key_actions: [{id, reason}], why: {key_action_id: "..."}}`.

`compose` starts from the expansion, drops pruned nodes (and what only hung on them; the
reachability rule decides), appends model nodes and edges, recomputes the ranking with the same
function as `expand_graph` (so the Key Action order is never the model's guess; the model
influences it only by pruning or excluding, each with a reason), validates, and raises
`SolutionInvalid` with the problem list. CLI: `hlidskjalf briefing compose <expansion.json>
<overlay.json> --out solution-graph.json` and `hlidskjalf graph check-solution <file>`. The
expansion JSON for the CLI comes from the turn log entry of `expand_graph` (the tool also
returns `expansion_id`, the turn-log line number, so the CLI can read it from the workspace
without the model copying it).

## MCP tool `expand_graph`

```
expand_graph(goals: list[str] = [], crisis_goals: list[str] = [], save: str | None = None)
```

- No `goals` → the catalogue: every Goal with title, domain and its Symptom metrics resolved on
  the save (so step 3 of the flow can choose Goals from Symptoms). No expansion.
- With `goals` → `Expansion.to_dict()` plus `expansion_id`.
- Registered like the other tools through `logged`, so the result lands in the turn log (the
  Unverified Claim check of M7 sees every number the Briefing may use). Errors (`GraphMissing`,
  `GraphInvalid`, unknown version) come back as `{"error": ...}` like the other tools.
- The graph is loaded once per server, version from the save header (`game_version`); a pack
  missing for that version returns an error that says so (ADR 0003: no silent fallback to
  another version). If the save's version differs from the pack's, the tool adds the existing
  version warning.
- Tests: the tool is listed with the right schema; a call writes one turn-log line; catalogue and
  expansion on the reference save; an unknown Goal and a missing pack give errors, not crashes.
  The M2 server tests are the template.

## Skill `hlidskjalf:consult` (`skills/huginn-consult/SKILL.md`)

The directory is `huginn-consult` (build plan "Shape"); the frontmatter `name` is `consult` so
the command is `hlidskjalf:consult`. The workspace `CLAUDE.md` template (M3) already routes
Consulting Campaigns to it; the increment checks that the name it references matches.

Flow (the build plan's eight steps; the skill is the checklist, the code does the rest):

1. **Save age.** `campaign_status`; stale → ask the Player to save again and stop.
2. **Situation.** `empire_overview`, `economy`, `progression`, `military` as needed; name the
   Situation in one or two sentences. Is there a Crisis (collapsing income, lost war)? Goals
   that answer it are Crisis Goals.
3. **Goals per Horizon.** Symptoms from the `expand_graph` catalogue and the tool results, plus
   the Player's stated ambitions. At most three Goals per Horizon. A Goal outside the catalogue
   is a model Goal.
4. **`expand_graph`** with the chosen Goals and `crisis_goals`.
5. **Prune and weigh.** Remove Remedies that do not fit this empire (each with a reason in the
   overlay), weigh `judgement` and `unknown` Obstacles (and say which were not checked against
   numbers), add model nodes only with `source: "model"` and a reason, read the Vicious Circles
   and their break point.
6. **Key Actions.** `compose` the overlay; the ranking comes back from the code. Name as many as
   the evidence supports (the build plan: no fixed "top 3"). Crisis Goals first.
7. **Strategy.** The ordered path through the Solution Graph (`unlocks` chains) from the first
   Key Actions to the Goals.
8. **Action Plan** by domain (economy, military, diplomacy, ...), each Key Action with its why,
   rating words (high/medium/low from the ratings), the Playbook Rule ids that apply and the
   rule text quoted.

Hard rules in the skill text:

- Every number comes from a tool result; never from memory, never calculated by the model.
  Display Names only as the tools return them.
- A Remedy that spends Unity is judged against `traditions.next_cost` (rule
  `unity-vs-next-tradition`): when the stockpile is below the next Tradition's cost the
  Briefing does not recommend spending it elsewhere, and says why, citing the rule id.
- Benchmarks are not used while the benchmark file is a draft.
- Fair Play: only what the tools return; no guessing about hidden facts.
- The model never writes HTML. The only files it produces are the overlay and (through the CLI)
  `solution-graph.json`.
- Speak the Player's language; the domain words stay as in the GLOSSARY.

A test (`tests/test_consult_skill.py`, like `test_setup_skill.py`) checks frontmatter, that the
skill names every tool and CLI command it needs and that those exist, and that it contains the
Unity rule's guard sentence and the "no HTML" rule.

## Open risks

- **Result size.** 35 nodes with text and effects can exceed the extract budget. Mitigation: effects
  capped, text only on nodes that survive depth cut and, if still too large, `text` omitted for
  `clear` Obstacles; measured in increment 2 and 4.
- **Weak metric coverage.** Many Obstacles are `judgement_only` (research has several); a
  Briefing then leans on the model. The tool reports `unchecked` per Remedy so this is visible,
  and frequent unchecked Obstacles are candidates for new registered metrics in maintenance.
- **Pending semantics** are my reading of the glossary and may differ from Julian's intent; the
  reading is stated here and in the module docstring, and costs one line to change.
- **Ranking is mechanical** and ignores context the model knows (a cheap Remedy that is
  pointless for this empire). That is what `prune` and `exclude_key_actions` with a reason are for;
  both are logged in the Solution Graph's `pruned`.
