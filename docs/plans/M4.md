# M4 plan: Mechanics Graph and Playbook for 4.5.2

Build plan: [M4](../build-plan.md). Terms: Mechanics Graph, Playbook, Playbook Rule, Benchmark,
Goal, Cause, Root Cause, Remedy, Obstacle, Actionable, Pending, Key Action
(see [GLOSSARY.md](../../GLOSSARY.md)). Decision: [ADR 0003](../adr/0003-mechanics-graph-built-per-version-by-developer.md).

**Done when** (from the build plan):

- The graph validates.
- Expanding the Goal "more naval capacity" from the Mechanics Graph alone yields Supremacy,
  Anchorages, naval-capacity technologies and Soldier jobs, each with its Obstacles.
- The benchmark draft is ready for review.

## Starting point (M0–M3)

- `GameData` (`gamefiles/`) parses `common/<category>/*.txt` with inline scripts and caches per
  game build. `Localisation` (`extract/names.py`) turns keys into Display Names and raises
  `UnresolvedName` when it cannot.
- `extract/computed/modifiers.py` already collects modifier contributions per empire (a `Ledger`
  keyed by modifier name, e.g. `country_naval_cap_add`). It answers "what applies to this
  empire"; the generator answers the campaign-independent question "what *could* produce this".
  The two stay separate; the generator reuses only `GameData` and `Localisation`.
- `src/hlidskjalf/graph/` is empty, `knowledge/4.5.2/` and `tools/` hold a `.keep`.
- Game version of the installed game: `launcher-settings.json` → `rawVersion` = `v4.5.2`.

## Three layers, one direction of dependency

```
generated facts  ←  curated graph  ←  Playbook Rules / Benchmarks (reference graph ids)
(game files)        (judgement)       (judgement)
```

- **Generated** (`knowledge/4.5.2/generated/*.yaml`): hard facts only — source, amount,
  requirement. Never edited by hand; regenerated per game version. Committed, so graph
  validation and tests do not need the game install.
- **Curated graph** (`knowledge/4.5.2/graph/*.yaml`): hand-written. Every number a node states
  lives in a generated fact the node links to; node text carries judgement, not figures
  (a figure in prose goes stale and is exactly what the Unverified Claim check hunts).
- **Rules and Benchmarks** reference graph node ids, never the other way round.

## Generated facts

### Format

One file per key quantity (14 files, names are the quantity ids):
`naval_capacity, energy, minerals, food, alloys, unity, influence, research, pop_growth,
stability, amenities, housing, building_slots, district_slots`.

```yaml
# knowledge/4.5.2/generated/naval_capacity.yaml
game_version: v4.5.2        # launcher-settings.json rawVersion
generator: 1                # bump when the output format changes
quantity: naval_capacity
facts:
  - id: naval_capacity.tradition.tr_supremacy_adopt.country_naval_cap_add
    effect: produces        # produces | costs | modifies (multiplier)
    modifier: country_naval_cap_add
    amount: 20
    amount_kind: add        # add | mult | per_unit (per job / per building / per pop)
    source:
      kind: tradition       # one of the scanned categories below
      key: tr_supremacy_adopt
      name: Supremacy       # Display Name from localisation (see below)
      file: common/traditions/00_supremacy.txt
    requirement: null       # or a list of condition lines, see below
```

Decisions:

- **Fact id = `<quantity>.<kind>.<key>.<modifier>`**, so ids are stable across regenerations
  and the curated graph can link to them. If one source yields the same modifier twice with
  different requirements (e.g. a base and a triggered block), the later gets a numeric suffix
  `…#2` in file order.
- **Display names are mandatory.** A source whose name cannot be resolved is *not* emitted
  with its key (CLAUDE.md rule); the generator collects them into
  `knowledge/4.5.2/generated/unresolved.txt` and exits non-zero unless they are listed in
  `tools/gen_mechanics_allow_unnamed.txt` (internal objects with no player-facing name, e.g.
  event-only modifiers, each with a reason).
- **Requirements are recorded, not evaluated.** `potential`, `allow`, `trigger` blocks of the
  source are rendered to flat condition lines (`has_technology = tech_x`,
  `owner.has_tradition = tr_y`). The Obstacle checks live in the curated graph, where a human
  chose which condition matters. Anything the renderer cannot flatten becomes a single line
  `unmodelled: <block name>` so a reader sees there is a condition.
- **Scripted values** (`value:bellicose_naval_cap`, `@variable`) are resolved through
  `GameData.scripted_variables` where numeric; otherwise `amount: null` plus
  `amount_expr: "<text>"`. No guessing.
- **Deterministic output**: facts sorted by id, keys in fixed order, no timestamps. The same
  game build gives byte-identical files (a test regenerates and compares).

### Scope: what is scanned

Per quantity a small table in `tools/gen_mechanics.py` lists the modifier keys and resource
names that count. Source categories scanned (all under `common/`):

| Category | What is read |
|---|---|
| `technology` | `modifier`, `country_modifier`; tech cost and tier for the Obstacle side |
| `traditions`, `tradition_categories` | adoption and finish `modifier`; tradition cost defines (links to `computed/tradition_cost.py`) |
| `ascension_perks` | `modifier` |
| `buildings`, `districts` | `resources` (produces/upkeep/cost), `planet_modifier`, `country_modifier`, slot effects, build cost and time |
| `pop_jobs` | `resources.produces/upkeep`, `*_modifier`, `triggered_*_modifier`, per-job amounts |
| `starbase_modules`, `starbase_buildings` | `country_modifier`, `triggered_country_modifier`, resources |
| `governments/civics`, `governments` | `modifier`, `country_modifier` |
| `policies`, `edicts` | per option `modifier`, edict cost |
| `static_modifiers`, `planet_modifiers` | modifier blocks (references from other sources point here) |
| `traits`, `species_archetypes` | pop growth, habitability-adjacent modifiers only |
| `deposits` | resource deposits (what the planet itself offers) |
| `megastructures`, `relics`, `agenda`-style country modifiers | `modifier`, `country_modifier` |

Quantity → keys (starting set; extended when a curated node needs a missing fact):

| Quantity | Keys / resources |
|---|---|
| naval_capacity | `country_naval_cap_add`, `country_naval_cap_mult` |
| energy, minerals, food, alloys, research | resource names in `resources` blocks; `*_produces_add/mult`, `*_upkeep_*`, `planet_jobs_<res>_produces_*`, `country_<res>_produces_*` |
| unity, influence | same pattern for `unity`, `influence`; `country_resource_*_mult` |
| pop_growth | `pop_growth_speed`, `pop_growth_speed_reduction`, `planet_pop_assembly_*`, `logistic_growth` defines |
| stability | `planet_stability_add`, `stability_*`, ethic-attraction-style stability modifiers |
| amenities | `planet_amenities_add`, `planet_amenities_no_happiness_add`, `planet_amenities_mult`, `planet_pops_*_amenities_*` (amenity upkeep per pop) |
| housing | `planet_housing_add`, `planet_housing_mult` |
| building_slots, district_slots | `planet_building_slots_add`, `planet_*_districts_max_add`, `planet_districts_*`; plus the `districts` definitions' own limits |

Not scanned in M4: events, decisions, megastructure construction chains, leader traits,
espionage, situations. They can add facts later; the generator's category table is the only
place to change.

### Implementation shape

`tools/gen_mechanics.py` is a thin CLI over a module `tools/mechanics/` (or a
`hlidskjalf.knowledge` package if tests need to import it; decided in the generator increment,
tests import whichever it is). Steps: walk categories → collect `(source, modifier-block,
requirement)` triples → match against the quantity table → localise → write. Reuses
`GameData.category()`; no second parser.

## Curated graph

### Files and ids

`knowledge/4.5.2/graph/<domain>.yaml`, one file per domain:
`naval_capacity, energy, minerals, food, alloys, unity, influence, research, pop_growth,
stability, amenities, housing, slots`. (The M4 criterion needs only the first; the others
follow in the increments of the plan.) A node id is `<domain>.<slug>`; ids are globally unique
and nodes may reference nodes of other domains, which is what lets graphs link up
(alloys need minerals and energy; naval capacity needs Unity for Supremacy).

### Schema (YAML, JSON Schema validated)

```yaml
version: v4.5.2
domain: naval_capacity
goals:                          # entry points: what a Briefing Goal expands from
  - id: naval_capacity.more
    title: More naval capacity
    symptom_metrics: [naval_capacity.fill]      # metric names, see below; optional
    causes: [naval_capacity.low_base_sources]
nodes:
  - id: naval_capacity.low_base_sources
    type: cause
    title: Few sources of naval capacity
    description: >
      Naval capacity is a flat base plus additive sources, then multiplied. …
    causes: []                  # deeper Causes; empty = Root Cause
    remedies: [naval_capacity.adopt_supremacy, naval_capacity.build_anchorages]
    facts: [naval_capacity.tradition.tr_supremacy_adopt.country_naval_cap_add]
  - id: naval_capacity.adopt_supremacy
    type: remedy
    title: Adopt the Supremacy tradition tree
    judgement: >
      Worth it when the empire is capacity-bound and Unity is not earmarked for a
      cheaper Tradition. …
    strength: high              # high | medium | low — effect size
    speed: medium               # high | medium | low — time to effect
    cost: high                  # high | medium | low — what it takes
    obstacles: [naval_capacity.supremacy_needs_unity]
    facts: [naval_capacity.tradition.tr_supremacy_adopt.country_naval_cap_add]
    rules: [unity-vs-next-tradition]    # Playbook Rule ids, optional
  - id: naval_capacity.supremacy_needs_unity
    type: obstacle
    title: Not enough Unity for the next Tradition
    check:                      # M5 evaluates this against the Snapshot
      metric: unity.stockpile
      op: "<"
      compare_to: {metric: traditions.next_cost}
    remedies: [unity.raise_income]      # an Obstacle gets its own Remedies → recursion
    facts: []
```

Rules of the schema:

- **Types and links.** `cause` → `causes[]`, `remedies[]`; `remedy` → `obstacles[]`;
  `obstacle` → `remedies[]`. Anything else is a validation error. A Cause with no `causes`
  and at least one remedy is a Root Cause; a Cause with neither is an error (dead end).
- **Required on every node:** `id, type, title, description` (cause/obstacle) or `judgement`
  (remedy). Remedies also require `strength`, `speed`, `cost` — M5 ranks Key Actions on them.
  Obstacles require `check`, so no Obstacle is prose-only; an Obstacle that cannot be
  expressed as a metric comparison uses `check: {judgement_only: true}` and M5 hands it to the
  model to weigh (the Briefing then says it was not checked against numbers). Used sparingly.
- **`facts`** are generated fact ids; the validator resolves each against
  `generated/*.yaml` and fails on a dangling id. Wildcards allowed for families:
  `naval_capacity.job.*.country_naval_cap_add` (resolves to ≥1 fact, else error).
- **Metrics** (`check.metric`, `symptom_metrics`) come from a registry
  `knowledge/4.5.2/graph/metrics.yaml`: name → path into the Snapshot extract document
  (e.g. `unity.stockpile` → `economy.unity.stockpile`) plus unit. The validator checks every
  used metric is registered; a test checks each registered path exists in the schema of the
  reference extract (so a renamed extract field breaks loudly). The exact path list is
  settled in the schema increment from the documented extract shape; the registry is also what
  M5's `expand_graph` evaluates, so M4 delivers the paths and M5 the evaluator.
- **Pending**: a Remedy may carry `pending_when: {metric, op, compare_to}` (e.g. jobs open and
  growth positive). Optional; M5 marks it Pending when true and the Obstacles are not.
- **Cycles are legal** (energy → jobs → pops → food → energy). The validator warns on cycles
  but only errors if a cycle has no exit remedy; M5 names them Vicious Circles. Authors
  mark a deliberate circle with `circle: <name>` on the nodes so M5 can name it and propose
  the cheapest point to break it (`break_point: true` on the cheapest node).
- **IDs of the same thing across domains are merged by id**, never duplicated: `unity.raise_income`
  is one node however many Obstacles point at it.

### Loader and validator (`src/hlidskjalf/graph/`)

- `MechanicsGraph.load(version)` reads `knowledge/<version>/graph/*.yaml` and the generated
  facts; indexes nodes by id; exposes `goal(id)`, `node(id)`, `fact(id)`. Loading a graph for
  a version other than the Snapshot's yields a version-mismatch warning (ADR 0003).
- `validate(version)` returns a list of problems (JSON Schema errors first, then the
  cross-file checks: unique ids, dangling links, dangling facts and rules, unregistered
  metrics, dead-end Causes, text containing digits flagged as a warning — see below).
- CLI: `hlidskjalf graph validate [--version v4.5.2]` prints problems, exit 1 if any error.
- JSON Schema lives in `src/hlidskjalf/graph/mechanics.schema.json` (packaged data) and is
  checked with `jsonschema` (`uv add jsonschema`).
- **Digits in prose**: `description`/`judgement` containing a digit run (other than inside a
  game identifier) is a validation *warning*, to keep figures in facts. Warnings do not fail.

### Test for the M4 criterion

`graph.reachable(goal_id)` is a plain depth-first walk (M5 builds the real, Snapshot-aware
`expand_graph`; this walk exists so M4 can prove the graph's shape alone). The test:
expanding `naval_capacity.more` from the loaded graph yields

- a Remedy for Supremacy (links the `tr_supremacy_adopt` fact),
- a Remedy for Anchorages (links the `starbase_modules` anchorage fact),
- a Remedy for naval-capacity technologies (links `tech_repeatable_naval_cap` etc.),
- a Remedy for Soldier jobs (links the soldier-job facts),

and every one of these Remedies has at least one Obstacle. A second test walks every goal in
every domain and requires every walk to terminate and every Remedy to be reachable from some
Goal (no orphans).

### Content outline per domain

Authoring order follows the plan; each domain starts from a generated fact list and the
Player-visible Stellaris concepts, in the domain language of the GLOSSARY.

| Domain | Goals | Typical Causes → Remedies |
|---|---|---|
| naval_capacity | more naval capacity | few sources → Supremacy, Anchorages (+ Naval Logistics Office), capacity techs, Soldier jobs, capacity edict/policy where it exists |
| energy | more / less negative energy | few producer jobs, high upkeep, low multipliers → generator districts and buildings, Technician jobs, techs, trade value, reducing upkeep |
| minerals | more minerals | miner jobs, deposits unused → mining districts, techs, Foundry-type conversions |
| food | food positive | farmer jobs, pop upkeep → agri districts, techs, hydroponics-like bonuses, resource converters |
| alloys | more alloys | foundry jobs short on minerals/energy → Foundry building, Metallurgist jobs, alloy techs, megacorp-free paths |
| unity / traditions | faster Tradition progress | few Unity sources → Unity buildings, Bureaucrat/Priest jobs, Ascension perks, tradition choice (links to the Rule on Unity vs. next Tradition cost) |
| influence | influence not wasted; positive income | low income, colony upkeep → Ruler/Envoy jobs, Imperial Fiat edicts, Starbase upkeep tuning; "at the cap" link to the Rule |
| research | more research | few researcher jobs, low multipliers → labs, Research districts, techs, Scientist leaders |
| pop_growth | faster growth | growth-rate bonuses, habitability, housing → Growth techs/traits/ edicts, Habitability fixes |
| stability | stability up | factions, ethics, buildings → stability buildings/edicts, faction handling |
| amenities / housing | amenities ≥ upkeep; housing ≥ pops | districts, buildings, techs |
| slots | more building / district slots | planet size, techs, designations → Ascension perks, techs, planet capacity |

Cross-domain Obstacles (Unity for a Tradition, alloys for a building, jobs for pops) are
expressed once as shared nodes (`unity.raise_income`, `housing.free_housing`,
`jobs.free_jobs`) which M5 merges.

## Playbook Rules (`knowledge/4.5.2/rules/*.md`)

One file per rule, YAML front matter then Markdown body:

```markdown
---
id: unity-vs-next-tradition
date: 2026-10-24
status: approved            # approved | proposed (proposed lives in docs/proposals/ only)
applies_to: [unity.*, naval_capacity.adopt_supremacy]
reason: >
  Julian's rule from the prototype: stockpiled Unity is judged against the next Tradition cost.
---
Judge stockpiled Unity against the cost of the next Tradition, never as an absolute number. …
```

- The three seed rules are approved by Julian in the build plan; ids:
  `unity-vs-next-tradition`, `influence-at-cap-is-waste`, `unemployed-before-colonies`.
- Loader `playbook.load_rules(version)` in `src/hlidskjalf/graph/` returns rules by id; the
  validator checks `applies_to` patterns match graph ids and that every rule id a node cites
  exists. `status: proposed` files are rejected in `knowledge/` (they belong in
  `docs/proposals/playbook.md`; CLAUDE.md of the loop: no further rules without Julian).
- Tests: seed rules load, ids unique, dates are ISO, the Unity rule is linked from a Remedy
  that spends Unity (so M5's Briefing can cite it).

## Benchmarks (draft)

`knowledge/4.5.2/benchmarks.yaml`, marked `status: draft`, with `provenance` (where each
value comes from) and `assumptions` per entry. Values per decade (2210 … 2290) for the main
figures: research, alloys, energy, minerals, food, Unity, influence income, naval capacity,
fleet power if the extract carries it, pop count, planet count.

Sources, in order of trust and honesty about it:

1. The reference Campaigns' archived extracts (vulkan, zygerrian) give *observed* values for
   one empire each; recorded as `observed: {campaign, date, value}`, not as a benchmark.
2. Values derived from game files (e.g. base job output × typical job count at a given
   planet count) are marked `derived`, with the formula in `assumptions`.
3. Everything else is a placeholder `value: null`, so nothing is invented. A benchmark with no
   source stays null and the review page says so.

`docs/benchmarks-draft.md` is generated from the YAML by a small script, one table per figure,
with draft banner, provenance and open questions for experienced players. Hold point:
review is Julian's (with experienced players); a German step list goes into
`docs/awaiting-julian.md`. No benchmark is used by a Briefing until its status is `reviewed`.

6. **Unity, Traditions, influence, research.**

Each curated-graph increment runs `hlidskjalf graph validate` and the full test suite; none
needs a headless `claude -p` run (M5 does that).

## Open risks

- **Requirement flattening** is the weak point of the generator: Clausewitz triggers nest
  `OR`/`NOR`/`AND` and scopes. Mitigation: render conservatively, keep `unmodelled:` visible,
  and curate Obstacles by hand.
- **Fact churn when a curated node links a fact** that disappears in a patch: dangling-fact
  validation fails loudly after regeneration, which is the point of per-version packs.
- **Completeness of the curated graph** is bounded by what the author writes; the model may add
  `source: "model"` nodes in a Briefing (M5), and frequent additions are promoted here.
